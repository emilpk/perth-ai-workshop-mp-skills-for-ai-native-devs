Part 2

Build a new feature

The bugs are fixed. Now the client wants favourites: signed-in shoppers can save products and see them on one page. Here's the whole loop, one skill at a time.

On Codex, type $ instead of /, for example $grill-with-docs. In an agent without commands, ask for the skill by name.

  1. Switch to Part 2

    In your copy of the shop, put your Part 1 changes aside, then switch branch.

    git stash -u
git fetch
git switch mash/part-2-new-features

    Rather your agent did it? Paste this in:

    Stash my changes, fetch, and switch this repo to the mash/part-2-new-features branch. Show me git status when you're done.

    Then run the setup skill once on this branch.

    /setup-matt-pocock-skills

    No copy yet, or the branch isn't there? Make one from the setup page with Include all branches ticked.

  2. Grill: agree what to build

    /grill-with-docs I want to add favourites to this shop: signed-in shoppers can save products and see them on a Favourites page. Keep each question short.

    Answer fast. If you don't know, say what you'd guess.

    What does this do?
    Why get interviewed?
    "Add favourites" hides a dozen decisions: what happens when you sign out, when a product is deleted, whether there's a limit. Settle them now and the agent builds what you meant.
    What's the "docs" part?
    As you agree on words, it writes them into GLOSSARY.md, and records hard-to-undo decisions in docs/adr/. Future sessions read them.

  3. Spec and tickets: write it down

    /to-spec
    /to-tickets

    Stay in the same session as the grilling. Don't clear yet.

    What does this do?
    The spec
    Turns the conversation into one issue describing the feature. No new questions.
    The tickets
    Splits the spec into small tickets, each a thin slice that works end to end, and notes which ones block which.

  4. Build one ticket, test first

    /clear
    /implement the smallest favourites ticket. Show me the failing test before you write the code.
    What does this do?
    Why clear?
    The ticket holds everything the agent needs. A fresh session keeps it sharp.
    Why the failing test?
    It proves the test can catch the problem. A test that never failed proves nothing.
    What else runs?
    Inside /implement, the tdd skill drives red-green-refactor and code-review checks the result against the spec and the repo's standards.

  5. Open a PR and review it

    Run the tests and show me the output. Then open a PR in my repo into mash/part-2-new-features using the PR template, and review it against REVIEW.md.
    What does this do?
    Who writes the PR?
    The agent, using the pr skill: a small picture of the change, evidence that it works, and how risky it is to merge.
    How risky is risky?
    Docs and copy: low. Ordinary changes: medium, one reviewer. Sign-in, checkout or CI: high, two reviewers. REVIEW.md spells it out for this repo.

  6. Merge, then retro

    Read the evidence, fix what matters, and merge it yourself. You land it, you own it.

    /retro

    Same session, before you clear. It suggests what to change so the next feature goes smoother.
